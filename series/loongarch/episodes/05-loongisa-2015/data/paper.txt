摘要 本文介绍了龙芯 CPU 的指令系统融合技术. 龙芯 CPU 在兼容 MIPS 指令系统的基础上进行
扩充, 增加 MIPS 中不具备但 X86 和 ARM 具备的、对二进制翻译影响很大的核心功能, 形成龙芯指
令系统 LoongISA. 在此基础上, 通过软硬结合的二进制翻译, 在龙芯 CPU 上运行 X86 和 ARM 的主
流系统及应用, 以弥补 MIPS 架构软件生态的不足. 实验结果表明, 通过软硬件协同优化, 龙芯指令
系统融合技术能够消除指令系统之间的壁垒, 使得 MIPS, X86, ARM 等不同指令集的软件能够融合
到统一的 LoongISA 平台上, 不加区别地高效运行.

关键词      龙芯 CPU MIPS 指令系统 龙芯指令系统 二进制翻译 兼容 软件生态



1   引言

  发展以 CPU 和操作系统为核心的自主软硬件已经成为中国的国家战略. 经过自 “十五” 以来的
十余年努力, 以 “龙芯”、“飞腾”、“申威” 为代表的中国自主 CPU 研发取得了长足的进展, 部分设计技
术达到了世界先进水平, 并在实际应用方面取得了若干突破, 出现了良好的发展势头. 随着自主 CPU
应用和产业化的不断深入, 相关的软硬件生态问题变得越来越突出. 虽然自主 CPU 都在不同程度上
采取了与国外 CPU 兼容的技术路线, 如 “龙芯” 在取得 MIPS 架构授权的基础上采取与 MIPS 兼容
的策略, 但比起主流的软硬件生态, 如 X86 在桌面/服务器领域的软件生态以及 ARM 在手持终端领
域的软件生态, 自主 CPU 在软硬件生态方面还处在很初级的水平, 严重制约了自主 CPU 的产业化.
   二进制翻译技术是实现跨指令系统兼容的重要手段. 二进制翻译技术在宿主机 (host) 上用软件
模拟出一个目标机/客户机 (guest) 指令系统兼容的 CPU 来, 从而在宿主机上执行客户机的二进制代
码, 达到兼容的目的. 如在 MIPS 计算机上模拟 X86 指令系统, 从而实现与 X86 兼容. 二进制翻译的
最大问题是效率问题, 用软件模拟的 CPU 比硬件直接实现的 CPU 慢很多. 如在 MIPS 计算机上使
用二进制翻译的方法运行 X86 二进制程序, 比起把该程序直接从源代码编译成 MIPS 指令并在 MIPS
计算机上执行, 运行速度一般有数量级的差异.

   通过硬件支持和软硬件协同可以有效提高二进制翻译的效率. 虽然不同的通用指令系统结构在功
能上都是完备的, 可以通过指令组合实现各种复杂的功能, 但指令的具体定义不同, 翻译起来就会走弯
路. 例如, X86 的每条运算指令都要产生 EFLAG 标志位, 如果用 MIPS 指令来模拟产生 EFLAG 标
志, 至少需要几十条指令, 如果在 MIPS 中增加专门产生 EFLAG 的指令, 则翻译起来就可以做到一
一对应. 又如, 访存指令都需要进行虚实地址转换, 从 X86 到 MIPS 的二进制翻译中, 要先把 X86 的
虚地址转换成 X86 的物理地址, 再把 X86 的物理地址作为 MIPS 的虚地址转换成 MIPS 的物理地址,
上述转换过程如果由软件实现, 需要十多条指令, 如果在 MIPS 的 TLB (translation lookahead buﬀer)
中增加一些特定的支持, 就可以直接把 X86 的虚地址翻译成 MIPS 的物理地址, 彻底消除虚实地址转
换的开销.
    龙芯 CPU 在兼容 MIPS 指令系统的基础上通过 MIPS 指令系统的 UDI (user deﬁned interface)
进行扩充, 增加 MIPS 中不具备但 X86 和 ARM 具备的核心功能, 形成龙芯指令系统 LoongISA, 使
得从 X86 和 ARM 的二进制到龙芯 CPU 的二进制翻译更加方便. 通过软硬结合的二进制翻译, 在龙
芯 CPU 上流畅运行 X86 和 ARM 的主流系统及应用, 以弥补 MIPS 架构软件生态的不足. 具体地说:
(1) 在 Linux 操作系统上进行从 X86 到 LoongISA 的系统级二进制翻译, 以运行 MS Windows 系统及
其应用. (2) 在 Linux 操作系统上进行从 X86 到 LoongISA 的应用级二进制翻译, 以运行基于 Linux 的
X86 应用. 虽然 Linux 上的多数应用都可以从开源社区获得并编译到 MIPS 环境下执行, 但有少数关
键商业应用如 Oracle 数据库没有开源版本, 需要建立基于 Linux 的从 X86 到 LoongISA 的二进制翻
译. (3) 在 Android 操作系统上进行从 ARM 到 LoongISA 的应用级二进制翻译, 以运行基于 Android
的 ARM 二进制应用. Android 系统支持 MIPS 指令集, 且其多数应用是基于 Dalvik 虚拟机的, 在
MIPS 系统上运行没有障碍. 但有少量对性能要求较高的应用中插入了 ARM 二进制码, 在 MIPS 指
令系统上无法直接运行, 因此需要建立从 ARM 到 LoongISA 的应用级二进制翻译. 龙芯 CPU 与 X86
及 ARM 兼容策略如图 1 所示.
    龙芯二进制翻译系统以 LoongISA 指令集兼容不同形态的 X86, ARM 指令集, 通过技术手段消
除单一指令系统的壁垒, 使得 MIPS, X86, ARM 等不同指令集的系统及应用软件能够融合到统一的
LoongISA 平台上, 不加区别地运行. 作为中间层的二进制翻译器, 充分利用本地硬件支持最大化地提
高模拟效率, 对上层应用软件提供目标指令集的虚拟运行环境. 不同二进制的应用软件与运行的硬件
平台之间不再具有决定关系, 用于支持软件开发的编译器、汇编器, 以往被绑定在各自特定的 CPU 之
上, 现在都能为 LoongISA 平台提供软件资源. 实验结果表明, 龙芯软硬结合的二进制翻译技术可以成
数量级地提高从 X86/ARM 到 MIPS 的二进制翻译效率.

2   相关工作

  跨指令系统的软件兼容是二进制翻译技术最重要的技术特征. 实现翻译代码的高效执行始终是该
技术领域的核心问题. 学术界和工业界针对这一问题, 展开了大量的研究工作.
    自 20 世纪 90 年代开始, 伴随着体系结构的多样化浪潮, 多种宿主机指令系统均针对 X86 目标
机提出了各自的二进制翻译平台, 例如, Digital FX!32[1] 用于 Alpha 宿主机系统, IA-32 EL[2] 用于安
腾 (Itanium) 宿主机, Transmeta CMS[3] 用于 Transmetas VLIW 指令系统. 此外, IBM 公司以 Power
体系结构为目标机, 提出了 DAISY[4] 二进制翻译系统, 以支持其 IBM VLIW 指令系统的推广. 上述
二进制翻译系统能够实现较高的执行效率, 例如, FX!32 在 500 MHz Alpha 处理器上达到了 200 MHz
X86 处理器的性能 [1] , IA32 EL 在执行部分 SPEC CPU2000 定点测试时能够平均达到本地编译执行
效率的 60%[2] . 然而, 上述二进制翻译平台针对特定目标机和宿主机, 缺乏针对不同目标机的适应性.
   随着体系结构的不断发展, 多样化的指令系统对二进制翻译技术提出了新的挑战, 针对多种目标
机的适应性成为关键需求. 该需求随着移动计算和云计算的迅速发展而受到广泛重视, 其根本原因在
于移动计算和云计算环境广泛包含异构平台. 例如, Qualcomm 和 ARM 将异构计算应用于移动设备,
即 ARM big.LITTLE 体系结构 [5] . 又如, Google 的大型机群由配置多样的多种指令系统构成 [6] . 上
述事例说明, 计算平台已经由传统的单一指令系统向多指令系统发展. 在此基础上, 移动计算和云计
算要求二进制翻译能够在统一的框架下实现跨多种指令系统的软件调度和执行. 学术界对这一课题进
行了开创性的探索. 文献 [7] 基于 QEMU 二进制翻译系统, 实现了异指令系统平台下的程序调度, 以
利用多种异构核的独有特性, 如降低平均功耗等. 其中, QEMU[8] 是一种广泛应用的可移植二进制翻
译系统, 能够适用于多种目标机 (如 X86, PowerPC, ARM, Sparc and MIPS) 和宿主机. 可移植性使得
QEMU 在诞生后的 10 年中得到了极为广泛的应用, 充分体现出可移植性 (即支持多种目标机和多种
宿主机) 在当前二进制翻译技术发展中的重要意义.
  然而, QEMU 的可移植性以大量牺牲模拟效率为代价. 评估表明, 未经优化的 QEMU 其模拟执
行效率 (以龙芯平台上模拟 X86 为例) 仅达到本地编译执行效率的不到 10%[9] . 其根本原因是 QEMU
为实现对多目标机和多宿主机的兼容, 使用体系结构无关的中间代码, 从而无法利用宿主机体系结构
特征, 难以对翻译代码进行深入优化. 对此, 龙芯平台已针对 X86 目标机提出了软硬件相结合的优化
方案 [9] , 即利用龙芯特有的虚拟化指令, 加速 X86 目标机程序的翻译执行效率, 基于 SPEC CPU2000
测试实现了 5∼10 倍的性能提升. 与此类似, 其他研究工作同样提出了利用宿主机特性, 优化二进制翻
译性能 [10∼12] . 然而, 上述方法针对特定目标机, 并未提出能够适用于多种目标机的优化方法.
    本文深入分析了二进制翻译系统的性能瓶颈, 提出了针对二进制翻译的通用软硬件协同优化技
术, 在保持目标机的移植性的基础上实现广泛的性能优化. 与前人的工作相比, 本文的工作强调更加
紧密的软硬件协同, 在少量的硬件支持下大幅度提高二进制翻译效率. 例如, 间接跳转始终是二进制
翻译的重要性能瓶颈, 前人的相关优化如 FX!32 提出的 shadow stack[1] 方法, HDtrans 提出的 return
cache[13] , inline[14] 方法均针对特定的间接跳转, 优化函数调用和返回的过程. 龙芯提出了利用内容相
联存储器 CAM 加速处理 X86 间接跳转的优化方法 [9] , 本文进一步展示了对于多目标机, CAM 方
法的适应性和挑战. 又如, 在系统级模拟中, 目标机虚地址到客户机实地址的转换过程是主要执行开
销 [15] . 针对 Power 平台上的虚拟化环境, 提出了上述地址转换过程的加速优化方法. 然而, 由于二进
制翻译中不同目标机的虚实地址转换机制的差异, 已有方法难以为二进制翻译中的地址转换提供通用
的优化. 本文展示了龙芯平台上适用于不同目标机的通用软硬件协同优化方法. 再如, 翻译代码效率
亦是二进制翻译的主要性能瓶颈. 已有研究基于 LLVM 优化引擎, 采用纯软件策略对翻译后代码进

3     体系结构对二进制翻译的支持

  指令系统是计算机软硬件的界面. 不同指令系统在总体功能上都是自成体系的, 在多年实践中积
累下来的成熟指令集如 X86, MIPS, ARM 等具有很大成分的共性, 都包括算术逻辑运算指令、转移指
令、访存指令、系统管理指令等指令, 通用寄存器、浮点寄存器、TLB、内存空间等运行时环境, 各种
例外入口, 包括用户态和核心态在内的多个系统状态等. 从高级语言程序编译成不同指令系统的二进
制代码, 其执行效率不会有很大区别.
    但由于不同指令系统的指令功能和运行时环境的具体定义不一样, 把一个指令系统的代码转换成
另一个指令系统的代码执行效率会有很大差别. 例如, X86 指令系统通过运算指令产生 EFLAG 标志,
转移指令判断这些标志值进行转移, 而 MIPS 指令系统直接比较寄存器的值并根据比较结果转移, 各
自效率都很高. 但如果要用 MIPS 的指令把每一条 X86 运算指令产生的 6 位 EFLAG 标志都模拟
出来, 就需要至少几十条指令来模拟一条 X86 运算指令产生的 EFLAG 标志. 又如, MIPS 有 32 个
通用寄存器, 而 X86 只有 8 个, 要在 X86 上模拟 MIPS 指令系统, 只能用 X86 的内存单元来存储
MIPS 中寄存器的值, 无疑会大大降低执行效率. 为了提高二进制翻译的效率, 要求宿主机指令系统不
论从功能还是运行时环境方面都要足够丰富, 可以方便地、一一对应地模拟客户机的所有指令功能. 为
此, 本文认真分析了 MIPS 和 X86 及 ARM 指令系统的差异, 在 MIPS 指令系统基础上增加了 MIPS
不具备、X86 和 ARM 具备而且对二进制翻译性能又是至关重要的指令功能, 形成了龙芯指令系统
LoongISA. LoongISA 以 MIPS 编码结构为基础, 在功能上是 MIPS, ARM, X86 的并集.
    一个指令系统通常包括用户态和核心态两部分功能, 不同指令系统的用户态功能差异小于系统态
功能差异, LoongISA 要实现 MIPS, ARM, 86 用户态功能的并集比较容易, 要实现 MIPS, ARM, X86
系统态功能的并集就难得多. 对于应用级的二进制翻译, 即在基于 MIPS 的操作系统中二进制翻译
X86 或 ARM 的应用程序, 应用程序所调用的系统调用直接由 MIPS 来实现, 二进制翻译的性能只取
决于 LoongISA 对 X86 和 ARM 用户态指令的支持程度. 对于系统级二进制翻译, 即在基于 MIPS 的
操作系统中二进制翻译 MS Windows 操作系统, 就要考虑对 X86 系统态功能的支持. 下面从指令功
能、运行时环境、核心态功能等 3 个方面介绍 LoongISA 对 X86 及 ARM 到龙芯 CPU 二进制翻译的
具体支持.

3.1   指令功能的扩展

      (1) 增加生成运算标志的运算指令以及根据运算标志进行转移的转移指令. X86 和 ARM 的运
算指令都能同时生成运算结果和标志, 转移指令则根据标志位转移. X86 有 6 位与运算结果有关的
EFLAGS 标志, 分别是进位标志 CF、奇偶标志 PF、辅助进位标志 AF、清零标志 ZF、符号位标志
SF、溢出标志 OF; ARM 有 4 位与运算结果有关的标志, 分别是符号位标志 N、清零标志 Z、进位标
志 C、溢出标志 V. X86 和 ARM 的转移指令主要判断这些标志位进行转移; 而 MIPS 没有定点标志
位, 其条件转移指令都是直接比较寄存器的内容作为转移条件, 如判断两个寄存器是否相等, 一个寄
存器的值是否大于 0 等.

      (1) 灵活的 TLB 格式支持客户机虚地址到宿主机实地址的转换由硬件直接完成. 系统级二进制
翻译过程中所有客户机访存指令的执行都要两级虚实地址转换, 即先把客户机的虚地址翻译成客户机
的物理地址, 再将客户机的物理地址作为宿主机的虚地址翻译成宿主机的物理地址. 在 QEMU 中, 对
于 X86 的一条访存指令, 需要 10 多条本地 MIPS 指令来模拟一次 TLB 转换行为. 由于普通程序中访
存指令的比例在 40%甚至更高, 所以软件虚实地址转换会极大地降低翻译效率. 因此需要在处理器的
TLB 中增加硬件支持, 由硬件完成从客户机虚地址到宿主机物理地址的翻译过程, 彻底消除虚实地址
转换的开销.
    为降低实现开销, LoongISA 的 TLB 可以同时存放 “宿主机虚地址 → 宿主机物理地址” 和 “客
户机虚地址 → 宿主机物理地址” 两种类型的页表项, 前一类型的页表项由宿主机操作系统中的普通
页表提供, 后一类型的页表项由二进制翻译虚拟机中维护的影子页表提供. 为了区分上述两类页表
项, TLB 中增加机器地址空间标识号域 (machine ID, MID), 主机页表项和客户机页表项分配有不同
的 MID. TLB 在进行虚实地址转换时, 不再使用 ⟨ASID, VADDR⟩ 而是使用 ⟨MID, ASID, VADDR⟩ 作
为匹配查找内容.

      (1) 增加系统状态提升虚拟机执行效率. 传统 MIPS 指令系统在进行系统级二进制翻译时, 客户机

“陷阱 — 模拟” 频繁发生, 将降低虚拟机的执行效率.

3.4     LoongISA 的指令编码

       LoongISA 中为提升 X86 和 ARM 二进制翻译效率所增加的指令、控制寄存器和例外等都是在兼
容 MIPS 指令系统的基础上通过 MIPS 指令系统的 UDI (user deﬁned interface) 进行扩展的. 在 MIPS
指令系统的 UDI 中, 提供了少量的指令编码槽可用于新增指令的编码. 为了弥补这些可扩展指令编码
槽数目有限的问题, LoongISA 除了利用部分扩展指令槽定义了一些最常用的新增指令外, 还通过定义
专门的前缀指令来扩展指令编码空间. 前缀指令可将其后接指令的含义进行重新定义, 或是为其后接
指令补充信息. 这种指令编码模式下, 后接指令或为已有 MIPS 指令, 或为采用 MIPS 指令编码风格
的自定义指令. 图 10 给出了扩展向量指令前缀 “XSETVS” 与 MIPS 向量指令 “ADDV.D” 结合, 仍
进行 “ADDV.D” 指令所表示的向量双字加操作, 只是通过前缀指令表明该指令操作将寻址 64 个 256
位的向量寄存器. 新指令操作数中 6 位寄存器号的最低 5 位记录在后接指令中, 最高位则统一位于前
缀指令中, 在译码时拼接成完整的寄存器号.

  通过实现二进制翻译系统原型来验证本文所提出的指令系统融合技术. 根据指令集的代表性和使
用的广泛程度, 选择了从 X86 到龙芯指令系统的二进制翻译系统, 其系统结构、实现方案、测试结果
对于从 ARM 到龙芯指令系统的二进制翻译系统具有示范意义.

4.1     系统结构

   龙芯 X86 二进制翻译系统 [9,18] 实现从 X86 到龙芯指令系统的二进制翻译. 该翻译系统基于跨平

   (1) 从 X86 到 LoongISA 系统级二进制翻译. 系统级二进制翻译是模拟一台目标机器的完整硬件,

CPU 的模拟. 为了运行 Windows 操作系统, 需要模拟完整的 X86 指令集, 包括特权态、用户态指令,
以及 MMX/SSE 等扩展指令集. 除了指令集之外, 还需要模拟完整的 X86 运行时环境, 包括寄存器、

4.2   二进制翻译系统优化

  龙芯二进制翻译系统在性能上发挥软件、硬件结合设计的优势. 系统集成了二进制翻译领域内主
要的成功优化方法, 包括动态优化 [19] 、基本块 chaining[8] 、自修改代码检查 [20] 等. 在此基础上, 除了
充分利用 LoongISA 提供的硬件支持外, 还在提高代码质量和并行翻译方面进行了进一步优化. 主要
包括以下几个方面:
  (1) 基于静态数据流分析的基本块优化方法. 传统二进制翻译过程一般以基本块为翻译单位, 在
翻译一个基本块时则以一条指令为单位. 一条客户机指令翻译为等价功能的数条本地指令. 为实现功
能等价, 一般针对每一条指令进行寄存器映射, 并在不同指令之间通过寄存器间的数据传递指令实现
对操作数的引用. 由于翻译过程的基本单位是单条指令, 因此翻译过程无法利用代码之间的数据相关
性信息, 使得同样的数据被生成或传递多次, 造成冗余代码的出现. 此外, 二进制翻译平台一般强调跨
平台通用性, 采用编译技术的中间代码机制. 中间代码往往具有平台无关性, 因此难以实现针对特定
本地平台相关的后端优化. 龙芯二进制翻译系统提出了一种数据流优化方法. 在中间代码中增加对于
宿主机体系结构的描述, 以数据流图描述宿主机指令的功能, 并通过数据流分析重建宿主机指令间的
数据流图. 基于数据流图能够消除冗余的数据生成、数据传递、数据读写等操作指令, 以及基本块中
的死代码, 最终提高翻译后代码效率.
  (2) 带有基本块私有缓存的间接跳转的优化方法. 间接分支跳转指令是指跳转指令的目标地址位
于一个寄存器或者内存单元中. X86 指令集大量利用了间接分支跳转指令, 实际的跳转目标地址只能
在运行时刻确定, 对于虚拟机则需要额外的地址查找和地址转换代价. 现有解决这一问题的方法包括
间接分支哈希表、目标地址内联、双地址返回栈等, 但是这些方法仍然未能充分利用查找目标的局部

      (3) 利用多核结构进行并行翻译优化. 为获得高质量翻译代码, 龙芯二进制翻译系统采用了重量
级 (heavyweight) 代码优化技术, 包括死代码消除、常量传播、寄存器提升、窥孔优化、动态优化等.
为减少重量级翻译优化过程对整体执行效率的影响, 龙芯二进制翻译系统提出并实现了代码执行和翻
译优化的多线程并行结构. 首先, 执行线程实现轻量级 (lightweight) 翻译过程, 并在翻译代码的执行
过程中提供用于热点分析的采样数据; 其次, 翻译优化线程在不中止执行过程的条件下完成热点代码
的分析和优化. 翻译优化线程根据采样数据确定执行热点, 进而将执行热点中的多个基本块组成超块,
最后利用重量级优化重新翻译超块. 在执行时间较短的程序中, 翻译优化过程在并行线程中进行, 因
此不会影响程序的执行效率和响应速度. 在执行时间较长的程序中, 重量级优化将生成高效的翻译代
码, 从而极大提高整体执行效率. 上述并行框架的主要开销在于多个线程对共享数据的访问, 包括采
样数据、基本块缓冲区、翻译后宿主机代码等. 龙芯二进制翻译系统将在并行框架中针对大量并行读
写过程设计简化的事务内存 (transactional memory) 模型, 以低开销的读写冲突检测和数据同步机制
代替高代价的锁操作, 从而保证并行框架的执行效率.


5     实验结果分析

5.1   实验环境

      本文的性能分析在龙芯 3A1500 四核处理器的 RTL 仿真验证平台上进行.
    龙芯 3A1500 四核处理器实现了前述龙芯指令系统 LoongISA, 其结构如图 12(a) 所示. 龙芯
3A1500 通过片上交叉开关集成 4 个 64 位的四发射超标量 GS464E 高性能处理器核和 4 MB 共享
三级 Cache. 该芯片还同时集成了 2 个 64 位 DDR2/3 控制器以及 2 个 HyperTransport 3.0 接口, 并
支持多芯片通过 HyperTransport 接口互连和跨芯片的全局 Cache 一致性.
      GS464E 处理器核结构如图 12(b) 所示. GS464E 处理器核的基本流水线包括 PC、取指、预译码、
译码 I、译码 II、寄存器重命名、调度、发射、读寄存器、执行、提交 I 和提交 II 共 12 级.
  取指与分支预测 GS464E 处理器核的取指部件每拍最多可以从指令 Cache 中取回 8 条指令在预
译码阶段进行分支预测. 预译码阶段每拍最多可处理 4 条分支指令, 但只有最后一条才允许是预测跳
转的分支指令. 经过预译码处理的指令后存入一个 64 项的指令队列中. 译码部件每拍从指令队列中
取出 4 条指令, 将其翻译成处理器内部的指令格式送往后续流水级, 其中最多包含两条分支指令. 取
指阶段的虚实地址转换通过指令 TLB 完成, 该 TLB 为 64 项全相联结构, 每一项存放一个页表项, 支
持可变页大小.
     在转移预测方面, GS464e 使用 128 项的分支目标缓存 (branch target buﬀer, BTB) 在取指流水级
利用 PC 来预测可能存在的跳转指令的目标地址, 并及时更新取指 PC. 预译码流水级将根据其他预
测器的预测结果对 BTB 的预测结果进行修正. 预译码流水级采用组合分支预测策略, 其中条件分支
指令的跳转方向通过一个 8 K 项的全局转移历史表 (global branch history table, GBHT), 一个 8 K 项
的局部转移历史表 (local branch history table, LBHT) 和一个 8 K 项的全局选择历史表 (global branch
select table, GBSEL), 并采用 13 位的全局历史寄存器 (global histiry registor, GHR) 进行预测. 另有
1 K 项的转移目标地址缓存 (branch target address cache, BTAC) 用于预测非程序返回跳转类指令的
目标地址, 以及一个 16 项的返回地址栈 (return address stack, RAS) 用于预测程序返回跳转指令的目
标地址.

和重命名浮点寄存器的物理寄存器堆各 128 项, 另有 32 项重命名 HI/LO 寄存器、32 项重命名 DSPCtrl
寄存器和 32 项重命名浮点控制寄存器.
   寄存器重命名后的指令送到保留站动态调度执行. GS464E 采用 3 个独立的分组保留站: 16 项的
定点保留站、24 项的浮点保留站和 32 项的访存保留站. 完成寄存器重命名的指令在送入保留站同时
也送入重定序队列, 用于确保按照程序顺序提交指令. 重定序队列共 128 项, 每拍最多可提交 4 条指
令. 转移指令在重命名后进入重定序队列和保留站的同时进入转移队列. 转移队列共 24 项, 用于维护
分支预测错误时回滚的顺序性.
   运算功能部件 GS464e 包含 2 个定点部件 ALU1, ALU2 和 2 个浮点部件 FALU1, FALU2. 定点
ALU1 和 ALU2 功能相同, 能够执行定点加减、逻辑运算、移位操作、比较操作、分支、乘除操作以及
所有 DSP 指令操作. 浮点 FALU1 和 FALU2 均能够执行浮点加减、取绝对值、取反、格式转换、比较
和点乘、除、开方操作. 为了降低转移队列的复杂度, 浮点转移指令只在 FALU1 中执行.
  访存部件 GS464E 处理器核的访存部件包含两个全功能的访存执行流水线, 每一个流水线都可
以每拍流水地执行一条 load 或 store 操作. load 或 store 操作经访存保留站发射, 并在访存专用定点
寄存器堆读取操作数后, 经过访存流水线执行. 访存执行包含地址计算、Dcache 读取、Tag 比较、数
据写回四级流水.
      GS464E 实现了非阻塞 Cache, 在一级数据 Cache 中未命中的访存操作将暂存在访存操作队列中
等待数据返回, 后续 Cache 命中的访存操作可以提前执行并写回. GS464E 采用统一的访存操作队列,
可存放 load 和 store 操作, 共 64 项.
      GS464E 中访存指令采用乱序发射机制, 即只要访存指令的操作数准备好即予以发射, 由访存操
作队列维护乱序发射的访存指令之间的正确执行序. 访存操作在访问完毕一级数据 Cache 后即进入访
存操作队列, 此时若发现存在因执行乱序而存在的数据相关违例情况, 则违例指令将回滚至访存保留
站等待再次发射执行.
      GS464E 的访存部件实现了两级 TLB 结构用于完成访存指令的虚实地址转换. 一级数据 TLB 的
大小为 32 项, 每一项可以装载一个 MIPS 标准双页; 二级 TLB 由两个部分组成, 一个 64 项的全相联
可变页大小的 CAM 部分, 以及一个 8 路组相联、每一路 128 项, 共计 1024 项的固定页大小的 RAM
部分.
    片上 Cache 层次 GS464E 处理器核使用了 3 级片上 Cache 层次, 其中一级指令 Cache(Icache)、
一级数据 Cache(Dcache) 以及数据和指令合用的二级牺牲 Cache(Vcache) 为每个处理器核内部私有,
第 3 级 Cache 为共享 Cache(Scache), 是所有处理器核共享的, 位于处理器核外. 一级指令 Cache 和一
级数据 Cache 均为 4 路组相联, 各 64 KB 大小. 二级牺牲 Cache 为 16 路组相联, 共 256 KB. 三级共
享 Cache 为 16 路组相联, 共 4 MB. 所有层次上的 Cache 使用相同 Cache 行大小, 为 64 字节. 一级指
令 Cache 采用伪随机替换算法, 其余各级 Cache 均采用 LRU 替换算法.
      GS464E 使用基于目录 (directory) 的 MESI 的 Cache 一致性 (Cache Coherency), 不支持升级
(Upgrade) 操作, 共享 (Shared) 块想要升级为独占 (Exclusive) 块, 需要先进行无效操作. Scache 会因
为一个处理器核的请求而向另一个处理器核发出一致性请求, 包括无效请求、写回请求及无效并写回
请求. 该一致性请求由被请求处理器核的 16 项的访存失效队列处理并给予响应.

5.2   初步实验结果

   龙芯 3A1500 处理器还处于研发阶段, 已经完整实现从 X86 到龙芯指令系统的二进制翻译硬件支
持, 对于从 ARM 到龙芯指令系统的二进制翻译硬件支持还处于由设计方案到工程实现的阶段, 因此
以 X86 到龙芯指令系统的二进制翻译系统原型进行实验.
   由于仿真环境只能提供有限的串口设备, 没有图形输出设备, 虚拟机无法模拟 Windows 所需要
的 VGA 显卡和显示器, 因此实验的测试程序是以文本模式启动 Linux 操作系统. Linux 的启动过程需
要计算机中所有组件协同支持, 反映了一个完整目标机器的综合模拟性能, 前文所述各项硬件支持和
软件优化, 无论是针对 CPU 核心计算、访存、以及外设的优化都能够在 Linux 启动过程中发挥相应
作用.
   测试包括以下 3 种模式:
   (1) 本地 MIPS 模式 (MIPS-Native). 把 Linux 通过本地 MIPS 的编译器进行编译, 生成 MIPS 机
器指令, 直接在龙芯平台上运行.
   (2) 未优化的二进制翻译模式 (X86-MIPS original). 把 Linux 通过 X86 的编译器生成 X86 机器指
令, 使用原版 QEMU 二进制翻译器的 i386-softmmu 模式在龙芯平台上模拟运行.
   (3) 优化的二进制翻译模式 (X86-MIPS optimal). 把 Linux 通过 X86 的编译器生成 X86 机器指
令, 并且通过具有硬件支持以及软件优化的优化二进制翻译器进行模拟运行.
   所有编译行为启用 GCC-O3 优化选项.
   表 1 给出了优化前和优化后二进制翻译系统的性能测试结果. 通过表中数据可见, 优化后 Linux
操作系统启动是优化前的 21 倍, 达到本地直接编译运行的 79.8%.
   需要说明的是, 上述实验是对龙芯 3A1500 在流片之前的初步验证, 实验平台是 EVE 仿真环境.
龙芯二进制翻译系统的优化还比较初步, 没有充分利用硬件支持和软件优化手段, 尚未反映最好的全
面优化效果, 还需要在后续工作中还会继续深入磨合和优化, 尤其是在流片后的正式芯片中进一步提
升其实用化的潜力.


6     结论及未来工作

  本文的研究表明, 通过在 MIPS 指令系统的基础上扩展 MIPS 中不具备但 X86 和 ARM 具备的
对二进制翻译影响很大的核心功能, 并通过软硬结合的二进制翻译, 可以大幅度提高从 X86(或 ARM)
到龙芯 CPU 的二进制翻译性能. 本文介绍的指令系统融合技术可以通过技术手段消除单一指令系统
的壁垒, 使得 MIPS, X86, ARM 等不同指令集的系统及应用软件能够融合到统一的 LoongISA 平台上,
不加区别地运行. 实验结果表明, 龙芯软硬结合的二进制翻译技术可以大幅度提高二进制翻译的性能.
  目前, 龙芯 3A1500 正在流片生产过程中, 龙芯二进制翻译系统也还比较初步, 有些硬件支持没有
充分利用. 本文后续的工作包括两个方面: 一是在龙芯 3A1500 流片后在基于龙芯 3A1500 的计算机

LoongISA for compatibility with mainstream instruction set
architecture
HU WeiWu1,2 * , JIN GuoJie2 , WANG WenXiang1 , ZHANG XiaoChun1 & WANG HuanDong2

1 Institute of Computing Technology, Chinese Academy of Sciences, Beijing 100190, China;
2 Loongson Technology Co. Ltd., Beijing 100095, China
*E-mail: hww@loongson.cn

Abstract This paper introduces the Loongson instruction set architecture (LoongISA), which extends the MIPS
instruction set architecture for compatibility with X86 and ARM mainstream instruction set architectures. New
instructions, runtime environments, and system states are added to MIPS through MIPS UDI (User Deﬁned In-
terface) to accelerate the binary translation of X86 and ARM binary codes to LoongISA binary code. In addition,
binary translation systems have been built based on LoongISA to run MS-Windows and its applications, X86
Linux applications, and ARM Android applications. LoongISA is implemented in the Loongson-3A1500 four-core
CPU product of Loongson Technology Corporation Limited. Performance evaluations using the Loongson-3A1500
FPGA veriﬁcation platform show that with hardware support, the binary translation system of Loongson 3A1500
can achieve very high eﬃciency.

Keywords Loongson CPU, MIPS instruction set architecture, Loongson instruction set architecture, binary
translation, compatibility, software ecosystem
